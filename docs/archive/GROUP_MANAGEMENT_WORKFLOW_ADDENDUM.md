# 流程编排：全局模板、项目实例与显式调用

本补充说明覆盖此前“分组管理/工作流组”方案。产品概念统一为“流程编排”，每份定义的类型为“架构”或“工作流”。普通聊天始终独立运行；只有用户明确选择或明确点名当前项目实例时才调用编排，不由 Supervisor 猜测意图。

## 1. 对象与生命周期

- **全局模板**：从左侧“流程架构模板”进入，创建/编辑项目无关的架构或工作流定义。模板保存名称、类型、窗口职责、窗口提示词、分支规则和布局，不创建会话，也不持有项目上下文。
- **项目实例**：用户在项目中选择模板后创建本地副本；用户可修改节点、提示词和布局，模板名称保持稳定。改全局模板不覆盖现有实例。实例只出现在所属项目的调用列表和 `/`、`+` 菜单中。
- **运行**：每次调用创建独立 run 与全新的运行会话。禁止拼入主对话、项目其他窗口或上一次 run 的历史。工作流只把本 run 上游节点的输出交给边相连的下游窗口；架构按明确的组织关系将任务交给被选中的职责窗口。
- 执行前始终出现 Y / N / O 确认：Y 执行本次，N 取消，O 返回编辑/建议而不执行。工具权限增加“流程编排”，默认“询问”；一次确认只授权本次运行。

## 2. 入口与页面跳转

```text
左侧「流程架构模板」 -> 全局模板列表 -> 创建/编辑模板
项目工作区 -> 流程编排 -> 项目实例列表 -> 从全局模板创建/编辑实例 -> 实例详情与运行记录
主对话 + 或 / -> 当前项目实例选择 -> Y/N/O 确认 -> 独立运行详情
```

全局模板页不显示项目会话或运行按钮。项目实例页显示架构/工作流图标、名称、类型、最近运行和编辑入口。无项目或无实例时明确显示空状态，不跨项目借数据。运行详情可见每个窗口的状态、增量内容、输入来源和最终输出；运行 UI 默认折叠过程，用户展开后查看详细过程。不能显示未发生的传递记录。

## 3. 编排交互

- 工作流采用轻量 Dify 式画布：Agent 对话窗口为主节点，可选条件分支；画布负责排列和连线，React Flow 保存节点位置/边。每个窗口可编辑职责、模型和自然语言任务提示词；提示词可引用“用户本次请求”和直接上游窗口输出。条件由一个窗口的自然语言结果驱动，避免大量专用转换节点。
- 架构采用 Paperclip 式清晰组织树：职责窗口按汇报/协作关系排列，可见指挥窗口与成员窗口；用户可选择实际接收任务的窗口。架构边表达组织关系，不代表每次都会群发。
- 拖动只更改布局；新建全局模板或项目实例时只保存定义，不创建 Agent thread。运行时才按需创建独立 run sessions。
- 编辑器保持画布、属性检查器和轻量节点工具栏三栏布局；选中窗口后在检查器编辑标题、职责、提示词、模型。支持缩放、平移、适配画布、撤销/重做和清晰的连接方向。避免扩展成通用低代码平台。

## 4. 后端与验证边界

- 全局模板存于应用配置根的 `.agents/templates/topology/`；项目实例存于项目根 `.agents/groups/`，运行日志及运行会话存于项目 `.agents/runs/`。所有读写 API 明确区分模板与 project_id。
- 后端检查项目归属、实例类型、权限 `whitelist_actions` 与显式确认；默认询问策略下没有确认令牌不能执行。确认凭据绑定一次 run，不能复用。
- 每个运行窗口使用新的 session ID 和仅本 run 的显式输入。运行事件/日志要能追溯到 run、node、来源和目标；对失败和空输出如实报告。
- 验收需在真实前端完成：创建并保存一个全局模板；在项目 A 创建本地实例并修改提示词，确认全局模板未改变；从 `+` 或 `/` 分别选择并真实调用工作流和架构；逐一确认 Y/N/O 的行为、模型流式输出、项目隔离和 run 历史；再切换项目验证实例不串项目。保留真实页面与 API/模型返回证据，不以单元测试替代操作验证。
